# Splunk SOC Home Lab
### Data Ingestion, Windows Event Analysis, SPL Querying & Security Alert Configuration

---

## 1. Project Overview

This project focuses on building a practical Security Operations Center (SOC) environment using Splunk as the primary Security Information and Event Management (SIEM) platform.

The lab integrates Windows security telemetry collected through Sysmon and event analysis results generated by Hayabusa. These data sources are ingested into Splunk, indexed, and investigated using SPL (Search Processing Language).

The main objective is to understand how security events are collected, organized, investigated, and transformed into actionable detections within a SIEM environment.

During this project, I configured data ingestion, created dedicated indexes, performed security log investigations, analyzed process and network activities, identified suspicious behavior, and configured a scheduled alert to monitor potentially unwanted external network connections.

### Project Objectives

- Configure Splunk to collect and index Windows security telemetry.
- Ingest Sysmon events and Hayabusa analysis reports.
- Understand index management and Windows event data organization.
- Perform security investigations using SPL queries.
- Analyze process creation and network connection events.
- Identify potentially suspicious process behavior.
- Configure scheduled alerts for security monitoring.
- Build a practical SOC investigation workflow.

---

## 2. Lab Environment & Architecture

The lab uses multiple security tools to collect and investigate Windows endpoint telemetry.

| Component | Purpose |
|---|---|
| Splunk | Centralized log collection, indexing, searching, and alerting |
| Sysmon | Windows process, network, and system activity monitoring |
| Hayabusa | Windows Event Log analysis and detection reporting |
| SPL | Searching, filtering, aggregating, and investigating security events |

### Data Flow

The general workflow implemented in this lab:

1. Sysmon generates detailed Windows system activity logs.
2. Splunk collects Sysmon events through the configured `inputs.conf` file.
3. Hayabusa processes Windows Event Logs and generates a CSV report.
4. The Hayabusa report is imported into a dedicated Splunk index.
5. SPL queries are used to investigate and correlate available event information.
6. Suspicious activity is identified and monitored through a scheduled alert.

## 3. Data Collection & Index Management

### 3.1. Sysmon Log Ingestion

Sysmon was configured as a Windows endpoint telemetry source.

Its event records provide visibility into different system activities, including process creation and network connections.

The `inputs.conf` configuration was used to enable the ingestion of Sysmon logs into Splunk.

A dedicated index named `sysmon` was configured as the destination for these events.

**Objective:**

Establish centralized visibility into Windows endpoint activities and make Sysmon telemetry searchable within Splunk.

### 3.2. Windows Event Channels

Different Windows Event Log channels were examined, including:

- Security
- System
- Setup

The purpose of this step was to understand how Windows organizes event records and how different event channels can be collected and assigned to appropriate Splunk indexes.

### 3.3. Hayabusa Index Configuration

A separate index named `hayabusa` was created to store Hayabusa analysis results.

Configuration details:

| Setting | Value |
|---|---|
| Index Name | `hayabusa` |
| Data Type | Events |
| Maximum Index Size | 500 GB |
| Data Format | CSV |

The Hayabusa CSV report was imported into the newly created index.

This allowed the generated detection results to be searched and investigated directly within Splunk.

**Objective:**

Keep Hayabusa detection results separate from raw Sysmon telemetry, allowing independent investigation and easier data organization.

## 4. SPL Querying & Security Log Investigation

SPL (Search Processing Language) was used to filter, aggregate, sort, and investigate security events.

The following investigations were performed using the ingested Sysmon and Hayabusa data.

### 4.1. Sysmon EventCode Distribution

The `stats` and `sort` commands were used to examine the distribution of Sysmon EventCodes.

**Objective:**

Understand which types of system activities are represented in the collected telemetry and identify the frequency of different event categories.

This provides an overview of the available endpoint data before performing more targeted investigations.

### 4.2. Hayabusa Detection Frequency Analysis

Hayabusa events were investigated using their `Level` and `RuleTitle` fields.

The `stats` and `sort` commands were used to identify the frequency of detection levels and rule matches.

**Objective:**

Understand which detection categories appear most frequently in the imported Hayabusa report and identify rules that may require further investigation.

### 4.3. Medium-Severity Detection Investigation

A filter was applied to isolate medium-level Hayabusa findings:

`Level="med"`

The resulting records included PowerShell and WSMAN COM-related detection rules.

**Objective:**

Narrow down the investigation to selected medium-severity findings and examine the associated event details.

These findings were treated as investigation leads rather than confirmed malicious activity.

### 4.4. Process Creation Investigation – Sysmon EventCode 1

Sysmon EventCode 1 was used to investigate process creation activity.

The `table` and `head` commands were applied to display selected process-related information and examine the resulting records.

**Objective:**

Review process creation activity and understand how endpoint process events can be investigated through Splunk.

Process creation telemetry can provide useful context when investigating unusual executables, command-line activity, and parent-child process relationships.

### 4.5. Network Connection Investigation – Sysmon EventCode 3

Sysmon EventCode 3 was used to investigate network connection events.

A frequency-based filter was applied using:

`where count > 5`

Loopback connections were excluded from the investigation to focus on other network connections.

**Objective:**

Identify recurring network connection activity and narrow the results to connections occurring more frequently than the selected threshold.

This investigation helped highlight processes and network destinations that could require additional security review.

## 5. Suspicious Activity Investigation

### 5.1. Identification of Unusual Network Activity

During the network connection investigation, the process `utweb.exe` was identified establishing frequent connections to multiple external IP addresses.

This activity was selected for further monitoring.

The investigation focused on:

- The process responsible for the connections.
- The frequency of outbound network activity.
- The number of external IP addresses involved.
- The presence of repeated connection patterns.

**Investigation Note:**

High-frequency outbound connections do not automatically indicate malicious behavior. The identified activity was treated as potentially suspicious and selected for monitoring rather than classified as confirmed malicious activity.

### 5.2. Detection Objective

The objective was to create a monitoring mechanism that could identify future search results matching the selected suspicious network activity pattern.

Instead of relying exclusively on manual investigation, a scheduled alert was configured in Splunk.

## 6. Splunk Alert Configuration

### 6.1. Alert Creation

A scheduled alert was created using Splunk's **Save As > Alert** functionality.

**Alert Name:**

`Supheli uTorrent Dis Baglantisi`

**Configuration:**

| Setting | Value |
|---|---|
| Alert Name | Supheli uTorrent Dis Baglantisi |
| Alert Type | Scheduled |
| Trigger Condition | Number of Results > 0 |
| Trigger Mode | Once |
| Status | Enabled |

### 6.2. Trigger Configuration

The alert condition was configured as:

`Number of Results > 0`

This means the alert is triggered when the scheduled search returns at least one matching result.

The trigger mode was configured as `Once`.

### 6.3. Log Event Action

A Log Event action was added to the alert configuration.

The following settings were applied:

| Parameter | Configuration |
|---|---|
| Event | `alert:$name$` |
| Event Format | `generic_single_line` |
| Destination Index | `main` |

The alert was enabled after completing the configuration.

**Objective:**

Create an automated monitoring mechanism that records matching alert events in Splunk for subsequent investigation.
